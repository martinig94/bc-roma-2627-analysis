# LBA Serie A 2026/27 — game-by-game data

Incremental collector for the Italian basketball league (Lega Basket Serie A) 2026/27 season,
built on the undocumented JSON API behind [legabasket.it](https://www.legabasket.it).
It runs every morning on GitHub Actions, collects any newly finished games, and commits
the updated dataset — so `data/` grows on its own through the season.

Season context: 16 teams, 30 rounds (andata/ritorno). Two Rome teams — **BC Roma** (team_id 1761,
ex Vanoli Cremona) and **Maxima Roma** (team_id 1762, ex Germani Brescia).

## Data

| file | grain | notes |
|---|---|---|
| `data/games.csv` | one row per game (all 240 scheduled) | scores, quarter scores, venue, attendance, coaches; `game_status` 2 = finished |
| `data/box_scores.csv` | one row per player per game, plus `team` and `total` rows | minutes, pts, FG2/FG3/FT made+attempted, reb (O/D), ast, stl, tov, blk, fouls, `val` (LBA efficiency), `oer`, `plus_minus`, `starter` |
| `data/pbp.csv` | one row per play-by-play event | period, clock, running score, player, event type (Italian: "2 punti segnato", "Rimbalzo difensivo", "Ingresso"/"Uscita" = substitutions…), shot type qualifier, **x/y court coordinates (0–100)**, zone |
| `data/teams.csv` | teams of the season | team ids are re-issued each season — don't join across seasons on id |
| `data/raw/<game_id>/*.json` | untouched API payloads | lets you rebuild the CSVs offline (`python -m lba_data.rebuild`) |

Coordinates: `x` runs along the length of the court (each team attacks one half; `side`
flips per team/half), `y` across the width. Percent of court, not metres — calibrate
against the 3pt line (~6.75 m) before computing distances.

## Run locally

```bash
pip install -r requirements.txt
python -m lba_data.collect            # pull whatever is new
python -m lba_data.collect --limit 2  # test run
python -m pytest -q                   # unit tests against a real Round 1 payload
```

## Analysis starter

```python
import pandas as pd
box = pd.read_csv("data/box_scores.csv")
players = box[box.row_type == "player"]
roma = players[players.team.isin(["BC Roma", "Maxima Roma"])]
roma.groupby(["team", "player_surname"])[["pts", "reb", "ast", "val", "plus_minus"]].mean()
```

## The site (GitHub Pages)

**Just want to edit a game page? See [weekly/HOW-TO-EDIT.md](weekly/HOW-TO-EDIT.md).**

`docs/` is a static site (built locally to preview, never committed; GitHub Actions builds and publishes it), generated by `python notebooks/weekly.py`. Team, season, author and the EuroCup file are set in
`weekly/config.json`. Every page has one dropdown at the top, **Opponents**: one entry per game that has an opponent analysis (which links to the BC Roma
snapshot of the same game). Every snapshot, including those of games without an analysis (e.g. an early EuroCup game), is reached from the
*BC Roma: situation, roster, form* section of the landing page:

| | what | data used | page folder |
|---|---|---|---|
| **BC Roma before the game** (link from the analysis) | BC Roma's situation before every game, **in both competitions** (LBA and EuroCup): LBA and EuroCup record, LBA standings, last results of both, last game's playing-time flag, team numbers (LBA and EuroCup columns), roster with photos, assist matrix and shot zones (LBA play-by-play), TS% vs PIR (LBA only, EuroCup only), every game so far | only games played before that game, in both competitions | `docs/snapshot/<date of the game>/` |
| **Opponent analysis** (the dropdown) | one per opponent and game, with the comparison table against BC Roma, results and standings, the opponent's roster with photos, starters and bench, scoring sources, shooting, hot spots, key players, lineups | only games played before that game: the league (LBA) plus the EuroCup, for the teams in the EuroCup file | `docs/opponent/<matchup folder>/` |
| **Game reviews** (landing page; **off by default**, switch `"reviews": true` in `weekly/config.json`) | post-game: quarters, margin chart, team numbers, PIR vs average, playing-time flag, box scores, round results | through that game | `docs/review/round-NN/` |

**Every week** (the GitHub Action runs every morning at 06:40 UTC: it collects the games finished the day before, runs `weekly.py` and commits the result when there is something new; EuroCup games, results and the games still to play come from the EuroLeague API: `eurocup_fetch.py` keeps the EuroCup rows of `weekly/schedule.csv` up to date, so the next EuroCup game gets its snapshot and analysis by itself):

```bash
python notebooks/weekly.py --collect    # pull new games, generate everything that is missing, build docs/
# then review and improve the pages it lists (see "Your pages" below), and push
git add -A && git commit && git push      # the site is rebuilt after a push that touches weekly/
```

`weekly.py --round 4` regenerates everything of one LBA round, `--game 2026-10-20` the snapshot of any game (stats corrections),
`--only snapshot,opponent,review` a subset; your text is never overwritten. The list of games (LBA from `data/games.csv`, EuroCup from
the EuroCup file, games still to play from `weekly/schedule.csv`) is `team_games.py`. A snapshot says when a game before it is not
in the data yet. The single steps are `snapshot_report.py --game DATE`, `opponent.py --round N`,
`weekly_report.py --round N` (review) and `build_site.py`.

* **Flags at the top of a page**: *Games still to be played before this one* (the page is a preview), *Played but not collected yet*
  (the data of an earlier game is missing; fixed by the next collection), and, for a game still to come, *Automatic draft, not reviewed
  yet* / *Work in progress*. The idea: the site first publishes everything automatically, then you review and improve. A page counts as
  reviewed when its page file (`weekly/games/<date>/snapshot.md` or `analysis.md`) has `reviewed: yes` in the header;
  without it the banner says draft (the page is still what was generated) or work in progress (you changed it). Pages with a hand-written README or `document.md`
  are reviewed by definition. `weekly.py` prints the upcoming games still to review, and the landing page shows the same on the cards.
* **Leaderboard** (header tab, `docs/leaderboard/`): Synergy team leaderboards, offence and defence, overall and by play type, for the EuroCup and LBA Serie A, both Roma teams highlighted; click a column header to sort a table (again to reverse) and the Rk column is renumbered by that column, click Rk to go back to Synergy's ranking. Data: the newest `data/synergy/leaderboards_<date>/` folder (four CSVs, see its README), pulled from Synergy in the logged-in browser with `synergy/leaderboards_pull.js` after each EuroCup / LBA game; the steps are in `.claude/skills/synergy-leaderboard/SKILL.md`. Push the new folder and the site rebuilds.
* **Goal, Methodology and Work plan** are pages of the site written in `weekly/pages/goal.md`, `weekly/pages/methodology.md` and `weekly/pages/work-plan.md` (edit them like
  any markdown file; `build_site.py` publishes them). **Comments** come from [utterances](https://utteranc.es): each page has a comment box
  at the bottom, and a comment is stored as a GitHub issue of this repository (one per page, label `comment`), so readers need a GitHub
  account. One-time setup: install the utterances app on the repository (https://github.com/apps/utterances); the repository is set in
  `weekly/config.json` (`comments`; remove it to switch the box off).
* **Editing from the page**: every page has an "Edit the text of this page" link that opens its markdown file in GitHub's web editor (the
  page file of a snapshot or analysis, the notes of a review; `document.md` or the README of an analysis written by hand; `weekly/pages/*.md` for Methodology and
  Work plan). Saving it commits to `master` and the workflow *Build and deploy the site* (`.github/workflows/site.yml`, also runs on
  changes under `weekly/`, `reports/` and `data/`) rebuilds and republishes the site in about a minute. People without write access get "Propose changes": GitHub forks the
  repository and opens a pull request that you merge. The repository and branch are `repo` and `branch` in `weekly/config.json`.
* **Landing page sections**: *Next games* (opponent analyses), *BC Roma: situation, roster, form* (a dropdown of the pre-game snapshots, the
  upcoming ones as cards, and a picker to compare two games) and, if switched on, *Game reviews*. The *Compare* page (`docs/compare/`, also in the header) is
  one static page: the numbers of every snapshot are embedded in it and the two situations are drawn side by side in the browser
  (`?a=<date>&b=<date>` in the address selects the games; each snapshot links to it with itself as B).
* **Sections that open and close**: on every content page each main heading (`##` in the markdown) is a section with a ▾/▸ marker that
  opens and closes it (plain HTML `<details>`, open by default), with **Collapse all** / **Expand all** buttons above the first one. The title,
  banners and intro before the first `##` stay visible. Nothing to do in the markdown files.
* **Highlighting table cells**: every page with a table has a floating **✎ Highlighter** button. With it on, pick a colour (five swatches) and
  a click on a cell highlights it (click again with the same colour to remove, with another colour to recolour; shift-click does the whole row), **Clear highlights** removes them all. It is for working live on
  a page (meetings, review sessions) and is kept in the browser of whoever clicks, not in the repository. For a highlight that stays
  for everybody, write `==text==` in the markdown file (for instance `| ==4.5== |` in a table written by hand, or in `document.md`).
* **Your pages** (snapshot and opponent analysis): one markdown file per game and page, `weekly/games/<date>/snapshot.md` (BC Roma before the
  game) and `analysis.md` (the opponent). They are written once, the first time the game is generated, and **never overwritten once you have worked on them**
  (a page still exactly as generated is refreshed when the default page gains a block, e.g. Assists or Turnovers; for a page you have edited, add
  the line `{{ assists }}` or `{{ turnovers }}` where you want the block). They are yours. `python notebooks/weekly.py --page 2026-10-24` prints their paths (creating them if missing). A page file is plain markdown:
  * a few header lines at the top: `title:` (name in the dropdown), `reviewed:` (`no` / `yes`) and `generated:` (leave it);
  * your text and your section titles: `##` headings, paragraphs, lists, `==highlights==`; reorder, delete or add sections freely;
  * **live placeholders** for the automatic content, one per line: `{{ roster }}`, `{{ comparison }}`, `{{ standings }}`, `{{ lineups }}`,
    `{{ team_numbers }}`, `{{ last_game }}`, `{{ assists }}`, `{{ zones }}`, `{{ efficiency }}`, `{{ season }}`..., and
    `{{ figure: 07_key_players }}` for any generated image. They are replaced when the site is built and keep refreshing when the data
    changes; delete the line to remove a block, move it to move the block. The comment at the top of each file lists them;
  * **your own plots and images**: put the file in the same folder (`weekly/games/<date>/`) and write `![caption](my_plot.png)` where you
    want it (drag and drop it with GitHub's "Add file / Upload files", or copy it locally). Ask Claude to draw a plot and it goes there.
  Text in `<!-- comments -->` is not published (the prompts of a new page are comments); sections that stay empty are left out.
  Pages written by hand (`reports/matchup_*/README.md`, `weekly/opponent/<folder>/document.md`) are shown as they are. **No automatic
  post-game review is generated or published** unless `"reviews": true` in `weekly/config.json` (the `reports/review` and
  `weekly/review` folders were removed, as unused; `weekly_report.py` recreates them); if switched on, reviews use `weekly/review/round-NN/notes.md` (`## key` sections: `key_points`, `story`, `tactics`, `players`, `next`).
* **Old-format analyses**: an analysis that is a hand-written page (`reports/matchup_*/README.md`, `weekly/opponent/<folder>/document.md`) and not
  a game page file is flagged: a banner *Old format* at the top of the page, " · old format" in the Opponents dropdown, a note on its card of the
  landing page, and a list in the output of `weekly.py`. Its tables and figures do not refresh with new data. It stops being flagged when
  it is replaced by a game page (`weekly/games/<date>/analysis.md`).
* **Automatic-only analyses of past games**: a generated analysis or snapshot of a game already played that is still exactly what was generated gets an
  *Archive, automatic only* banner and " · automatic only" in the dropdown or the snapshot list (and a line in the output of `weekly.py`), so readers know no
  analyst text exists. Setting `reviewed: yes` in its page file, or editing it, removes the flag.
* **Layout**: `weekly/template/page_snapshot.md.j2` and `page_analysis.md.j2` are the default of a new page (change them and only new pages
  change), `blocks.md.j2` holds the automatic blocks (the macros behind the placeholders, shared by all pages), `review.md.j2` the review,
  `site.html.j2` the look. To add a block: add a macro to `blocks.md.j2`, put its numbers in `auto` (the generator) if needed, and add
  `{{ name }}` to the pages that should show it. See `notebooks/pages.py` for how pages are read and expanded.
* **Standard structure of an analysis** (`weekly/template/page_analysis.md.j2`, the default of every new analysis page, LBA or EuroCup): Key points ·
  results and standings (with the results timeline) · the two teams compared (table, basic stats, space for the Synergy radar) · opponent roster ·
  starting five and bench · scoring sources, tendencies and shooting maps · key players (shooting, other stats) · ball movement (assists,
  turnovers) · lineups · what to expect · highlights. A section that is still empty shows a **grey box** ("This section will be filled when the
  game is reviewed"): the `{{ pending }}` line of the page file; replace it with your text. Change the template and only new pages change.
* **Starting fives**: every analysis has the grid of the opponent's last 5 games (LBA and EuroCup), `11_starting_fives.png`: starter (S, minutes), bench minutes, absences. The snapshots show the assist matrix and the shot zones of BC Roma for LBA and, when it has EuroCup games, for the EuroCup too (`assists_eurocup.png`, `zones_eurocup.png`).
* **EuroCup analysis**: a EuroCup game gets exactly the same analysis as an LBA game (same sections, same figures: hot spots, assists, lineups
  included), built only from EuroCup data (the other EuroCup teams are the league reference). The data comes from the EuroLeague API through the
  [`euroleague-api`](https://github.com/giasemidis/euroleague_api) package: box scores and shot zones in `data/eurocup_2026_raw.txt`, and
  `data/eurocup/pbp.csv`, the play-by-play in the same columns as the LBA `data/pbp.csv` (shot positions from the package's shot data, assists
  linked to the preceding made basket), so the LBA code reads both. Both files are appended by `eurocup_fetch.py` in the daily run. The games still to play are written into `weekly/schedule.csv` by `eurocup_fetch.py` (rows replaced at each run, so changed dates follow;
  `analysis` = `matchup_<home>_vs_<away>_before_<date>`; a row you wrote by hand, or whose folder has a hand-written README / `document.md`, is never touched); the daily run, or
  `python notebooks/opponent.py --eurocup <date>`, generates the analysis and creates `weekly/games/<date>/analysis.md`. A folder with a hand-written README or
  `document.md` there is kept as it is (Manresa).
* **Next games** on the landing page: the next game to play in each competition (LBA from `data/games.csv`, the others from
  `weekly/schedule.csv`), each with its snapshot and opponent analysis. Those pages are generated ahead of the game and regenerated
  by `weekly.py` whenever new games enter the data (`n_before` in their `auto.json`) (`date,time,competition,opponent,home,analysis`, `home` 1/0; `analysis` =
  the `reports/matchup_*` folder). Add a row for every EuroCup game.
* **A document of your own for an opponent**: put it as `weekly/opponent/<matchup folder>/document.md` (images next to it). It is
  shown first, exactly as written, and the automatic report of that folder follows under "Automatic data report", so nothing of either
  is lost. The Manresa page is built like that from the Word document (`pandoc doc.docx -t gfm`, highlights kept as `<span class="mark">`).
* **Manresa photos**: `python notebooks/manresa_fetch.py` downloads them (EuroLeague roster API, needs network access to
  `api-live.euroleague.net`) into `data/manresa/photos/<surname>_<initial>.jpg`; or put your own jpg files there under those names
  (e.g. `notae_j.jpg`, `villar_r.jpg`). Then run `python notebooks/manresa_report.py --before 2026-10-18` and `python notebooks/build_site.py`:
  the pictures appear in the roster table of the document and in the automatic report.
* **Opponent figures** come from `matchup_report.py`, `lineups_report.py` and `standings.py` (`--before <date>`); each team's EuroCup
  games are added when the team is in the EuroCup file. Hand-written opponent pages get the roster with photos appended automatically
  (`roster.json` next to their README). Photos come from the league media server (box-score `player_p_key`); the Manresa report takes
  them from the EuroLeague roster API when `manresa_fetch.py` runs (`data/manresa/photos/`).
* **EuroCup data**: `python notebooks/eurocup_fetch.py` (run by the daily workflow; needs the EuroLeague API, i.e. network access to
  `api-live.euroleague.net`) writes `data/eurocup/results.csv` (every game of the season, through the
  [`euroleague-api`](https://github.com/giasemidis/euroleague_api) package), `people.csv` and `photos/` (rosters with headshots, from the
  club "people" endpoint). The snapshot of a EuroCup game shows the **EuroCup table of BC Roma's group** as of that date, computed from
  `results.csv` (a group = the teams connected through the schedule; ranking by wins, head-to-head, point difference), never the LBA table.
  Without `results.csv` the page says the standings are not available yet. EuroCup box scores come from the file
  (`data/eurocup_2026_raw.txt`: box scores and shot zones of every EuroCup game played, appended by `eurocup_fetch.py`, so the daily run keeps it current).
* **Roster positions and heights**: `data/roster.csv` (new players are appended blank). Photos: `data/photos/` (fetched automatically; the only copy, `build_site.py` puts the ones a page needs into `docs/`, so report folders hold no photos).
* **Look**: light and sober, in the BC Roma palette. The logo is `weekly/assets/logo.png` (copied to `docs/assets/`, also the favicon); the
  colours are the variables at the top of `weekly/template/site.html.j2` (logo gold for borders and rules only, a deeper gold for links, warm
  near-black text; every text colour has a contrast of at least 5:1 on white).
* **Official sites** on the landing page are the `links` list in `weekly/config.json` (label and url).
* **Another team or season**: change `weekly/config.json`; the code has no team name in it.
* Enable the site once in the repository settings: Pages, Build and deployment, Source "GitHub Actions" (the workflow `site.yml` builds and publishes `docs/`, which is not committed).

## Caveats

* Not an official API. Endpoints were mapped from the site's network traffic in Sept 2026 and can
  change without notice — if a run fails, check `lba_data/api.py` first.
* Be polite: the collector sleeps between games and only fetches games it hasn't stored yet.
* Box scores appear within minutes of the final buzzer, but stats can be corrected in the days
  after. The collector doesn't re-fetch a game once stored; delete `data/raw/<game_id>` and
  re-run to refresh one.
* Playoffs are a separate championship id; add it with `--champ <id>` when the time comes.
